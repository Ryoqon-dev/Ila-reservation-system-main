# 데이터 관리

이 문서는 운영 자료를 내보내고 학기를 마감하거나 과거 기록을 정리하는 절차와 전체 복구용 백업을 설명합니다. 관리자 웹 화면의 CSV와 운영자 PC의 전체 DB/키 백업은 목적과 포함 범위가 다릅니다. 구현 근거는 [data-management.mjs](../../lib/data-management.mjs), [data-export.mjs](../../lib/data-export.mjs), [data-manager.tsx](../../src/data-manager.tsx), [secure-backup.mjs](../../scripts/secure-backup.mjs)입니다.

## 조회와 사용량

관리자 `dataOverview`는 예약·벌점·감사 건수, 오래된 날짜, 현재 유효 벌점, 최근 완료 마감 30건을 반환합니다. DB 용량은 D1 응답의 `size_after`가 유효한 숫자일 때만 표시합니다. 값이 없으면 `null`이며 0으로 추정하지 않습니다. 삭제 후 DB 파일이 즉시 작아지는 것은 보장하지 않습니다.

외부 Cloudflare 사용량 연동은 선택 사항입니다. 연결 없이도 건수·용량·CSV·마감·정리는 동작합니다. `data_metrics`에는 계정 ID와 `ROOM_KEY`에서 파생한 키로 암호화한 조회 토큰을 저장합니다. 연결 저장·해제는 관리자 재인증을 요구하며, 저장 전 실제 조회 성공을 확인합니다. 조회는 고정 GraphQL 주소에 보내고 `redirect:'manual'`로 3xx를 거절하여 토큰을 다른 주소로 전달하지 않습니다. 제한 시간은 8초, 같은 UTC 날짜의 캐시는 최대 5분입니다. 실패하면 같은 날 마지막 값 또는 `null`과 `stale`을 반환합니다.

반환 통계는 연결 계정 범위이며 이 사이트 하나만의 수치가 아닐 수 있습니다. 앱의 `FREE_LIMITS`는 코드에 고정된 비교 기준이며 실제 현재 요금제의 한도를 검증한 값으로 취급하지 않습니다. [data-metrics.test.mjs](../../tests/data-metrics.test.mjs), [metrics-runtime.test.mjs](../../tests/metrics-runtime.test.mjs)는 모의 서버/로컬 Workers 경로를 검증하며 사용자 운영 토큰을 조회했다는 증거는 아닙니다.

## CSV 두 경로

| 경로 | 반환·포함 범위 |
| --- | --- |
| `dataExport` POST | 데이터 관리 화면의 페이지 JSON. `bookings`, `penalties`, `audit`, `resets`, `clubs`별 명시적 열 목록을 사용하고 브라우저가 CSV를 생성합니다. 예약 CSV는 대표자·연락처·상태·입퇴실 확인값을 포함하나 메모·추가승인 사유는 제외합니다. |
| `export` GET | 기존 관리자 예약 CSV 직접 응답. 예약번호·시간·동아리·대표자·전화번호·상태·사진 확인값에 더해 추가승인 사유와 메모도 포함합니다. |

두 경로 모두 관리자 전용이지만 열이 같지 않습니다. 비밀번호·해시·키·세션·예약 확인코드·이미지·임원 학번/연락처를 내보내는 전체 DB 덤프가 아닙니다. 자유 입력 벌점 사유나 감사 대상에 비밀을 적으면 일반 업무 텍스트로 내보내질 수 있으므로 그곳에 인증정보를 기록하지 않습니다.

`dataExport`는 200건씩 날짜·정렬값·ID 커서로 읽고 `data_revision`을 시작 전후로 검사합니다. 페이지마다 자료 버전이 달라지면 409로 중단하여 서로 다른 시점의 행이 조용히 섞이지 않도록 합니다. 브라우저는 한 파일 100,000건 초과 시 저장을 중단하고 범위를 나누도록 안내합니다. 이는 [data-manager.tsx](../../src/data-manager.tsx)의 클라이언트 제한입니다.

`csvDocument`는 UTF-8 BOM, 따옴표·쉼표·줄바꿈 이스케이프를 적용하고 `= + @ -` 및 제어문자로 수식을 시작할 수 있는 값을 텍스트로 처리합니다. CSV에는 개인정보가 포함될 수 있으므로 다운로드 파일도 운영 자료로 보호합니다. 전체 복구에는 아래의 DB와 키 백업이 따로 필요합니다.

## 학기 벌점 마감

화면의 “초기화”는 행을 지우는 대신 `penalty_closures`로 기존 벌점을 완료 작업에 연결합니다. `penalty_records` 뷰의 `reset_id`가 없는 유효 행만 현재 합계에 포함됩니다. 현재 학기는 달력에서 자동 산출하지 않고 마지막 마감 후 남은 자료로 정합니다.

1. 관리자 데이터 관리에서 마감 처리명과 전체/개별 동아리를 선택하여 `prepareDataAction(action:'reset')` 미리보기를 만듭니다.
2. 동아리·건수·점수·처리명을 확인합니다. 전체 마감에는 비활성 동아리도 포함됩니다.
3. 해당 작업의 대상 CSV를 마지막 페이지까지 내려받고 파일 내용을 직접 확인합니다. 서버는 `export_ready`로 전 페이지 요청 완료를 확인하지만 실제 디스크 저장·파일 열람까지 증명할 수는 없습니다.
4. 파일 확인 체크와 정확한 확인 문구, 현재 관리자 비밀번호와 새로운 TOTP/복구 코드를 입력합니다.
5. 결과의 처리 건수와 완료 상태, 현재 점수 및 마감 이력을 확인합니다.

확인 문구는 전체 `전체 벌점 초기화`, 개별 `개별 벌점 초기화`입니다. 이 작업은 예약·동아리 계정·사이트 설정을 초기화하지 않습니다. 원래 벌점 값은 남지만 현재 합계에서 빠지고 일반 벌점 CSV에 마감 처리명과 함께 나타납니다. `penalty_periods.start_date`는 실행 당일로 올려 그보다 과거 날짜에 새 벌점을 부과하지 못하게 합니다. 마감 기록 수정·취소를 자동으로 되돌리는 UI는 없으므로 대상 선택이 틀렸다면 임의 SQL 수정보다 전체 백업과 관계를 먼저 검토해야 합니다.

## 과거 기록 영구 정리

| 정리 종류 | 실제 삭제 조건 |
| --- | --- |
| `bookings` | 예약 `date < before`의 모든 상태. 연결 `booking_access`를 먼저 지운 뒤 예약 삭제 |
| `penalties` | `date < before`이고 이미 마감했거나 `voided=1`인 행만 삭제. 현재 유효 벌점 제외; 연결 마감 행은 CASCADE |
| `audit` | `substr(created_at,1,10) < before`인 감사 행 |

기준일은 오늘보다 이전이어야 하고 기준일 당일은 포함하지 않습니다. UI에서 삭제한 예약의 `DELETED` 상태와 이 정리의 물리 삭제는 다릅니다. 영구 정리 후 예약·확인서·벌점 원본은 웹 화면에서 복구할 수 없습니다. 계정·비밀번호·이미지·현재 설정·`data_jobs` 마감 이력은 정리 종류로 선택할 수 없습니다.

실행 순서는 미리보기 → 대상 CSV 전부 다운로드·직접 확인 → `backupConfirmed:true` → `이전 기록 삭제` 확인 문구 → 관리자 재인증입니다. 삭제는 최대 250건씩 배치하며 각 단계에서 권한·자료 버전·작업 단계를 다시 검사합니다. 진행 중 다른 업무 자료가 바뀌면 이미 완료한 배치는 유지되고 나머지 작업은 멈출 수 있습니다. 남은 건수를 다시 확인·내보내기한 후 진행하세요. 이미 완료한 단계의 재요청은 동일 단계를 다시 삭제하지 않도록 처리합니다.

## 작업 안전장치와 한계

`data_jobs.owner`는 미리보기를 만든 관리자 세션 해시입니다. 다른 접속으로 작업을 이어갈 수 없습니다. 미리보기는 30분 유효하며 완료 작업은 이력으로 남습니다. 실행은 CSV 완료·명시 확인·단계 번호·업무 버전 일치가 필요합니다. 실행 요청 때 `authorized_until`이 지났으면 재인증을 요구하며 성공적으로 가져간 배치마다 이 시각을 현재부터 5분 뒤로 연장합니다. 모든 업무 변경의 감사 INSERT가 `data_revision`을 증가시키므로 미리보기와 내보내기 사이 변경을 탐지합니다. 직접 SQL로 업무 행만 바꾸고 감사를 남기지 않는 운영은 이 계약을 벗어납니다.

작업 시작 claim, 마감/삭제, 감사, 처리 건수·버전 갱신은 같은 배치로 실행합니다. 감사 실패 시 업무와 작업 상태도 함께 롤백합니다. 이 원자성은 한 배치의 보장입니다. 여러 삭제 배치를 전부 자동 역복원하는 기능은 없습니다. 범위를 나누고 먼저 전체 백업을 확보하는 이유입니다. 관련 검사는 [data-management.test.mjs](../../tests/data-management.test.mjs)입니다.

## 전체 DB와 키 백업

기존 운영 폴더에서 `BACKUP_DATA.cmd` 또는 다음 명령을 실행합니다. 이 명령은 실제 원격 D1 export를 수행하므로 로컬 단위 테스트가 아닙니다.

```powershell
npm run backup
```

DB 백업 암호와 키 백업 암호를 각각 12~256자로, 서로 다르게 정하고 각 두 번 확인합니다. 입력은 화면에 표시하지 않으며 서버에 백업 암호를 저장하지 않습니다. 실제 키·두 암호를 잃으면 암호문 DB만으로 복구할 수 없습니다.

| 결과 | 포함 정보 |
| --- | --- |
| `backups/<stamp>/database.ila-backup` | 생성 시각·D1 SQL·실제 `wrangler.json` 설정. `secrets` 원문을 포함하지 않음 |
| `.secrets/key-backups/<stamp>.ila-keys` | 생성 시각·`.secrets/runtime.json`의 실제 비밀키. 별도 암호 사용 |

백업 컨테이너 형식은 `ILA-BACKUP-v1`이며 JSON 데이터를 gzip으로 압축하고 scrypt(`N=131072,r=8,p=1`)로 얻은 키를 사용해 AES-256-GCM으로 보호합니다. 각 파일은 32바이트 salt·12바이트 IV·인증 tag를 갖고 `database`/`keys` 종류를 추가 인증 데이터에 묶어 종류 조작을 거절합니다. 복호화기는 이전 scrypt `N=32768` 백업도 읽습니다.

저장 함수는 암호화 직후와 파일 저장 후 두 번 복호화하여 원본과 일치하는지 검사하고 새 파일만 쓰는 `flag:'wx'`를 사용합니다. D1 export의 평문 SQL은 임시 `.secrets/backup-<UUID>.sql`로 받았다가 성공·실패 모두 `finally`에서 제거합니다. 프로세스 강제 종료 후에는 남을 수 있습니다.

`protectLegacyBackups`는 `backups/` 아래 이름이 `database.sql` 또는 `runtime.json`인 기존 파일을 재귀 탐색해 검증된 암호화 사본을 만든 뒤 원문을 지웁니다. 모든 임의 이름 SQL 파일이나 디스크 복구·동기화 서비스 버전까지 제거하는 기능은 아닙니다. 키 백업은 DB 백업과 다른 보호 위치/매체에도 보관하세요.

## 복호화와 실제 복구의 구분

`RESTORE_BACKUP.cmd` 또는 다음 명령은 파일과 해당 암호를 받아 복호화합니다.

```powershell
node scripts/restore-backup.mjs
```

도구는 선택한 백업 파일 옆의 새 `recovered-<시각>/`에 `database.sql`, `wrangler.json`, `runtime.json` 또는 구형 백업 원본을 씁니다. 잘못된 암호·변조 파일은 거절하고 운영 DB에 자동 import하거나 운영 키를 덮어쓰지 않습니다. 생성 폴더에는 원문 SQL과 키가 있을 수 있으므로 비공개로 보호합니다.

실제 서비스 복구 전에는 DB 백업과 대응하는 키 백업, Worker 버전, DB ID와 공개 범위, 스키마의 보안 전환 상태를 함께 확인해야 합니다. 먼저 격리된 복구 환경에서 키로 개인정보·방 비밀번호를 읽을 수 있는지, 관리자 MFA·동아리 로그인·확인서·예약/벌점 관계가 정상인지 확인한 후 운영 반영 방법을 결정합니다. 저장소에는 이 판단을 대신하는 자동 운영 복구 절차가 없습니다. 복구가 끝난 평문 폴더도 안전하게 정리해야 합니다.
