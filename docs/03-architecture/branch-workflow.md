# 브랜치 운영과 검증

`main`은 안정·배포 기준이며 기본 브랜치로 유지합니다. `develop`은 개발·통합 브랜치입니다. 주제별 `feature/*`, `fix/*`, `docs/*` 브랜치를 `develop`에서 만들고 검증 후 `develop`에 PR로 통합하는 것을 권장합니다. `develop`에 직접 작업할 수도 있습니다.

1. 작업 전 `git fetch origin`으로 원격 상태를 확인하고 `develop`에서 작업합니다.
2. `npm ci`, `npm run check`, `npm run build`, `npm test`를 실행합니다. 테스트 일부가 `dist/`를 사용하므로 빌드 후 테스트합니다.
3. `develop → main` PR을 생성하고 변경 사항, CI, 충돌 및 배포 영향을 확인한 후 병합합니다. 기본 대상 브랜치가 `main`이므로 작업 브랜치의 PR을 만들 때 대상이 `develop`인지 확인합니다. 실패한 검사나 미해결 충돌이 있으면 병합하지 않습니다.
4. 긴급 수정은 가능한 한 `fix/* → develop → main`으로 진행합니다. 긴급 예외도 PR을 남기고 수정 사항을 `develop`에 동기화합니다. `main` 직접 push, force push와 삭제는 금지합니다.

## GitHub에서 강제할 설정

2026-11-06 확인 시 이 저장소는 비공개이고 `main`은 보호되지 않았습니다. GitHub API의 Ruleset 및 Branch Protection 조회는 현재 요금제에서 비공개 저장소에 해당 기능을 사용할 수 없다는 403을 반환했습니다. **현재 문서와 CI만으로 직접 push, force push, 삭제 또는 관리자 우회를 차단할 수 없습니다.** 저장소를 공개로 바꾸거나 유료 요금제를 도입하는 결정은 별도입니다.

지원 가능한 환경이 되면 `main`에 PR 필수, 관리자 포함, force push 및 삭제 금지, 최신 기준 필수 상태 검사 `CI / verify`와 `CI / main-source`를 설정하고 우회 권한을 최소화합니다. `main-source`는 `main` 대상 PR의 출발 브랜치가 `develop`인지 검사합니다. GitHub 기본 PR 필수 설정만으로는 출발 브랜치를 제한하지 못합니다. 필수 검사 지정 전 실제 PR에서 정확한 검사 이름과 실행 결과를 확인하세요. 1인 개발 환경에서는 본인 승인 불가로 막히지 않도록 승인 인원은 0명으로 시작하고, 검토자가 생기면 1명 이상을 검토합니다.

보호 설정을 적용한 뒤에는 설정을 다시 조회하고 권한이 있는 테스트 계정으로 직접 push 차단, 잘못된 출발 브랜치의 PR 검사 실패, `develop → main` PR 검사 및 병합 가능 여부를 검증합니다. 보호 기능을 우회하거나 실제 `main`을 변경하는 시험은 별도 승인과 안전한 시험 계획 없이 수행하지 않습니다. 보호 전에는 제한된 저장소 쓰기 권한과 수동 PR 검토가 보완책이며 기술적 차단과 동등하지 않습니다. PR에서 CI 정의가 수정될 수 있다는 점도 검토해야 합니다.

GitHub merge 자체는 Cloudflare 배포가 아닙니다. 배포는 검증된 `main` 커밋으로 별도 승인과 [배포·운영 절차](deployment-and-operations.md)에 따라 수행합니다. 기존 배포 도구는 브랜치를 기술적으로 확인하지 않으므로 배포 담당자가 소스 커밋을 확인해야 합니다.
